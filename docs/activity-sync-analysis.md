There is no public-only import setting in the inspected web or mobile implementation. This report interprets that choice as declining private-activity permission on Strava's authorization screen. Confirm the screen and exact error before attributing the incident to that flow.

**Permissions explain why declining private access can fail.** Both [web OAuth](../internal/web/server.go#L958) and [mobile OAuth](../internal/web/server_mobile.go#L201) request `read,activity:read_all,activity:write`. They omit `activity:read`. The [callback](../internal/web/server.go#L984) passes only the authorization code to the connection helper; granted scopes are neither checked nor stored. Consequently a successful login can start a sync without the required activity access. Ordinary `read` does not grant activity reads. Reconnecting with broader access also does not automatically restart the initial import because it is [only scheduled on first connection](../internal/web/server.go#L1053).

Strava distinguishes `activity:read` (Everyone and Followers, excluding privacy-zone data) from `activity:read_all` (also Only You and privacy-zone data). Request the limited scope for the limited mode, validate the actual grant, and request broader access only for the broader mode. Treat write access as a separate capability. If the product promises strictly Everyone activities, enforce visibility filtering too: limited OAuth access still includes Followers. Unknown visibility should not qualify for a strict public-only filter. [Strava authentication documentation](https://developers.strava.com/docs/authentication/).

**The worker can turn waiting into permanent failure.** [Process jobs](../internal/storage/store.go#L513) allow ten failed attempts. [Retry handling](../internal/jobs/runner.go#L260) increments that counter for 429 responses, waits five to ten minutes without a Retry-After header, and then [replaces the cause](../internal/jobs/runner.go#L80) with `max attempts exceeded`. There is no application-wide cooldown: the next eligible activity can call Strava immediately. The [client](../internal/strava/client.go#L110) reads overall quota headers only on errors; it ignores the separate read-quota headers and successful-response usage. Token refresh errors are plain strings, so they also bypass typed API-error classification.

**Processing includes more than downloading an activity.** [Ingestion](../internal/ingest/ingest.go#L52) fetches metadata and streams. [Stats processing](../internal/processor/stats.go#L49) then performs map lookups per stop, with another road lookup for qualifying stops without a traffic light. A single map failure aborts stats processing before stats/stops are saved. [The final apply stage](../internal/web/server_apply.go#L146) fetches metadata again and may fetch streams again, computes facts, and optionally writes to Strava. A failed description/hide update fails the whole job even when imported data and calculated stats already exist. Some fact lookup/read errors are instead logged and skipped, so a completed job does not always mean every enrichment succeeded.

**Activities without streams need an explicit outcome.** A stream HTTP error returns before metadata is persisted. Empty successful streams are accepted, but [zero GPS points](../internal/ingest/ingest.go#L41) are treated as incomplete ingestion on subsequent runs, causing another download. Persist metadata independently and distinguish streams unavailable, not fetched, fetched, and failed. A known manual/indoor activity can finish with unavailable GPS facts; distinguish that from a deleted/inaccessible activity or unexpected malformed stream. Do not blindly suppress every 404.

**Errors are difficult to find today.** The [admin page](../internal/web/templates/admin.html#L41) already shows raw errors for sync and activity jobs, but the normal activity/mobile response has no import status. [Job queries](../internal/web/server.go#L1264) limit to the newest twenty jobs globally before filtering by user, so another user's activity can hide all of this user's jobs. The pending count is global. The sync job completes when enumeration/enqueueing finishes, independently of child processing. Ordinary processing failures stored as retries generally do not reach the runner's error log, because recording the retry returns success. Initial enqueue failure is only logged.

Show one persistent, owner-scoped import status on the activities page and mobile API. Track discovery separately from processing, retain an import ID on child jobs, and report discovered, imported, processed, pending, skipped, failed, and warning counts. Do not present an exact percentage until discovery has a stable total. For example: “240 activities processed; 760 waiting. Strava's daily allowance is used up. Resumes at 02:00.” Format the actual reset time in the user's timezone.

| --- | --- | --- |

Store structured `provider`, `stage`, `error_code`, HTTP status, retry time, and correlation ID with the job. Log state transitions with job/import/user IDs, elapsed time, and quota usage, preserving the last provider cause after retry exhaustion. Keep tokens, authorization codes, route coordinates, raw provider bodies, and full query URLs out of user-facing errors and routine logs. Overpass transport errors can include a URL containing coordinates. Operator diagnostics should use controlled, redacted details.

**The load is dominated by API calls and GPS points.** Current costs for 1,000 newly imported activities are approximately:

| Work | Current cost |
| --- | --- |
| List the last year | About 365–366 requests: this action uses one-day windows, including empty days. |
| List with a year-sized window | About 10–11 pages at 100 activities/page for a populated window. “Fetch all” also scans empty years from 1970. |
| Initial ingestion | 2,000 requests: metadata plus streams. |
| Apply stage | Another 1,000 metadata reads, up to 1,000 stream reads, and up to 1,000 updates. |
| Maps | Per-stop/route/place queries, potentially dozens per activity, reduced by cache hits. |
| GPS storage | Illustratively, 1,000 one-hour activities sampled each second produce 3.6 million point rows. Actual durations/sampling need measurement. |

For GPS rides with enabled facts, expect roughly 4,000–5,000 Strava requests plus listing before retries. Even a 30-day initial window at 1,000 activities/year is roughly 82 activities, enough for several hundred calls.

Quotas are shared by the application. Published default non-upload limits are 100/15 minutes and 1,000/day; the documented ten-athlete upgrade has 200/15 minutes and 2,000/day. Actual response headers/settings determine this app's allowance. Daily reset is midnight UTC, short reset is on quarter-hour boundaries, and over-limit short-window requests still consume daily allowance. Activity updates also count against non-upload quotas. Large backfills therefore need multiple quota windows. [Strava rate-limit documentation](https://developers.strava.com/docs/rate-limits/).

Implement a shared scheduler using both `X-RateLimit-*` and `X-ReadRateLimit-*` on all responses. Persist cooldowns, reserve capacity for new activities and interactive operations, and distribute backfill work fairly between users. Page through a fixed date range with a saved cursor; prioritize recent history. Deduplicate pending work by user/activity/stage and make page enqueueing plus cursor progress atomic. Separate fetch, local analysis, map enrichment, and optional publishing so retries retain completed work and do not repeat downloads. Reuse the ingestion snapshot; refresh mutable descriptions only when publishing requires it.

Keep concurrency bounded and add explicit HTTP/job deadlines plus renewable job leases before expanding worker count. Current [Strava clients](../internal/strava/factory.go#L37) fall back to an HTTP client without an overall timeout, and the runner uses the application lifetime context, so one hung request can occupy the single runner. Coordinate token refresh per user as well.

SQLite is a reasonable starting point at this activity count, subject to measurement. It already has WAL and a busy timeout, but [one shared connection](../internal/storage/store.go#L164). Add indexed job ownership/state/due-time columns, appropriate activity user/time indexes, and completed-job retention. Measure DB wait time, disk/WAL size, peak memory, request count, queue age, and per-stage latency using 1,000 and 10,000 synthetic activities. The [route-preview query](../internal/storage/store.go#L1744) reads every point for displayed activities before sampling; store simplified previews during ingestion instead. Web/mobile lists cap at 100 activities, so add pagination to make large histories navigable. No production throughput benchmark was performed here.

**Privacy needs lifecycle handling as well as ownership checks.** Normal web/mobile activity reads and downloads enforce ownership; the public landing page does not show activities. Importing private activities does not by itself make their routes public in WeirdStats. However, several concrete gaps remain:

- The current importer stores everything allowed by the token, including raw GPS and heart-rate/power streams. There is no saved import-visibility preference. Apply the user's policy during discovery, fetch, webhook processing, and reprocessing; a scope downgrade must also address previously stored broader data.
- [Webhook handling](../internal/webhook/handler.go#L79) records delete/deauthorization events but only processes activity create/update. Existing GPS data can bypass metadata refresh, leaving stored visibility stale. Apply deletion and privacy transitions, revoke disconnected authorization, and prevent later jobs from resurrecting removed data. Strava sends delete/create transitions for changes to/from Only You when using limited activity scope. [Strava webhook documentation](https://developers.strava.com/docs/webhooks/).
- [Disconnect](../internal/web/server.go#L1182) deletes the local token but retains imported data and work. [Account deletion](../internal/storage/store.go#L1216) misses `jobs` and `activity_stops`; stop rows retain precise coordinates. Specify retention clearly, cancel active/queued jobs, remove all owned data, and use tombstones or authorization generations to prevent in-flight work from recreating it.
- [Legacy migration](../internal/web/server.go#L1026) transfers user-1 data to the connecting athlete when the legacy token's athlete ID is zero. Require positively verified athlete identity before reassignment; this is a conditional cross-user exposure even though ordinary read endpoints check ownership.
- [Overpass queries](../internal/maps/overpass.go#L163) send precise locations to external map services. Private activity access also increases available location detail. Minimize queried geography, exclude sensitive route portions, consider cached regional extracts, and explain this processing. Location-derived facts such as cafes and landmarks [default to automatic posting](../internal/web/weirdstats_facts.go#L74), so analysis permission, private-data access, and publishing preferences need separate controls. Historical imports should not unexpectedly publish location facts or overwrite descriptions.

**Recommended delivery order.** First fix/read-check scopes on web and mobile, retain meaningful job errors, expose owner-scoped progress, and prevent quota waits from exhausting attempts. In parallel priority terms, close the legacy ownership and deletion gaps before expanding onboarding. Next split processing stages, reuse fetched data, add deduplication/fair quota scheduling, and make no-GPS and map failures explicit partial outcomes. Then validate the larger synthetic workloads and optimize measured database/map costs.
