Activity sync follow-up — 2026-09-08

The [investigation](activity-sync-analysis.md) identified reproducible implementation defects. The affected production job has not been inspected, so these fixes do not establish which failure that user encountered.

Implemented:

- Web and mobile OAuth request both limited and full activity-read capabilities, validate the returned grant, and persist its scopes. Private access and write access can be declined independently. Reconnecting resumes failed/blocked work. Reducing access atomically removes previously imported broader data and starts a fresh import, including when the user disconnected first. Limited Strava access includes Everyone and Followers activities; it is not a strictly Everyone-only filter.
- A shared Strava transport reads overall and read quotas on successful and failed responses. Persisted cooldowns survive restarts. Quota waits do not consume failure attempts. Backfills reserve 10% of each allowance, capped at 10 requests per short window and 100 per day, for recent activity and explicit requests. Actual provider headers determine resets and limits.
- Discovery uses saved pagination over a fixed date range. Enqueueing each page and advancing its cursor is atomic. Pending activity/stage work is deduplicated, users receive turns across a backlog, and recent-sync/publishing jobs have priority. Existing jobs receive indexed owner/activity/parent fields through schema migration. The runner remains bounded to its existing concurrency; adding replicas still needs coordinated leases and quota admission.
- Ingestion saves metadata before streams, remembers successful empty streams, and accepts missing streams for known manual/indoor activities. Unexpected stream errors remain visible. The feed explains when GPS statistics are unavailable. Base analysis, optional map enrichment, and optional publishing have separate jobs; downstream failures preserve completed analysis. Publishing refreshes the mutable description and reuses stored GPS streams. HTTP requests and processing stages have deadlines, and token refresh is coordinated per user.
- Web and iOS show owner-scoped processing counts, safe failures, job references, retry actions, reconnect guidance, and local reset times. Web status polls every 15 seconds; iOS refreshes with the feed. Provider bodies and query URLs are excluded from job errors. Worker logs include the error code and, for Strava responses, status, request ID, and read-quota usage. Legacy raw job errors are hidden in normal and admin views.
- External map enrichment and automatic publishing require separate opt-ins in Settings. Both default off, including for existing accounts until a preference is saved. Historical backfills do not automatically update Strava. Automatic publishing applies to activity-create events; updates still refresh local data. Consent is rechecked before external map requests and automatic writes. Changing the map preference applies when an activity is next processed. Explicit publishing remains available independently of automatic publishing.
- Activity delete/privacy webhooks invalidate stored routes, stops, statistics, facts, previews, related events, and jobs. Deauthorization removes the account's stored data. Webhook permission checks, invalidation, and enqueueing are transactional. Connection IDs, activity versions, guarded writes, and removed-job checks prevent stale background work or token refresh from restoring deleted data. Legacy ownership reassignment requires a matching athlete ID. Disconnect cancels jobs and removes credentials while retaining imported data, as explained in Settings; Delete account removes that data too.
- Web/mobile feeds have stable cursor pagination, including tied timestamps. New imports store small route previews so feed requests avoid repeatedly reading full GPS traces; older rows fill the cache on first use. Overpass's in-memory cache is bounded and expired entries are removed.

The expected initial import cost is now approximately two Strava reads per new activity plus listing, before retries. At 1,000 activities that is roughly 2,010–2,011 requests with 100-item pages. Optional publishing adds a metadata read and, when content changes, a write. Optional map processing has a separate request cost. A backfill can still span multiple days under the app's actual shared quota; adding workers does not remove that constraint.

Validation uses in-memory SQLite and local HTTP mocks, with no production tokens or private activity fixtures. Regression coverage includes limited OAuth grants, downgrade after disconnect, atomic downgrade rollback, shared quota reset/restart behavior, reserved interactive capacity, no retry-budget consumption for 429, safe retry exhaustion, current publishing consent, deletion and stale-write fences, delayed webhooks, missing streams, cached previews, owner isolation, and cursor ties. Synthetic queues at 1,000 and 10,000 jobs exercise deduplication and user fairness. Full Go tests, the race detector, Go vet, and an iOS simulator build are the release checks.

Remaining operational and product work:

- Inspect the reported user's redacted production job/error and the application's real rate-limit headers before claiming incident attribution. Deploy the changes, reconnect that user to obtain a recorded grant, and observe the resumed import through at least one quota reset. No production deployment or live import has been verified here.
- Profile representative GPS-heavy imports at 1,000 and 10,000 activities: API calls, queue age, stage latency, DB wait time, memory, disk/WAL growth, and feed latency. The queue tests do not simulate millions of GPS point rows. Use those measurements to choose worker count, storage retention, and map-query batching.
- Add configurable completed-job/event retention and operator dashboards for provider errors, quota consumption, and oldest pending work. Current UI counts are per user across retained jobs, not a separate history of import runs; completed means the base processing stage completed, while optional stages are reported separately.
- Introduce reconciliation for missed/out-of-order privacy webhooks, plus resumable map substeps or geographic batching if map-heavy activities exceed stage deadlines. Scope downgrades conservatively reimport all retained history because the old database cannot reliably distinguish previously downloaded privacy-zone data.
- If the product adds a strictly Everyone-only option, persist that preference and enforce exact visibility during discovery, fetch, webhook processing, and reconciliation. Current limited OAuth access also includes Followers. Further location minimization, sensitive-area exclusions, external-provider retention, and backup erasure need an explicit product/operations policy. Consent changes cannot recall a request already sent, and deleting local data cannot erase third-party request logs.
